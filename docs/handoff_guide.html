Setup & Handoff Guide

Complete step-by-step instructions for deploying the intelligent ServiceNow Demo Orchestrator to a new local machine.

1. Prerequisites

  • Download Node.js

    The MCP server requires Node.js to bridge the REST API. Download and install version 18 or higher from nodejs.org.

  • Download Claude/Cursor Desktop

    You must use the local Desktop application for MCP support. Download it directly from claude.ai/download (for Claude) or cursor.com (for Cursor).

  • ServiceNow Access

    You will need an active Developer Instance or Sub-Prod environment with admin privileges to deploy the backend script.

2. The Local MCP Server

  • Clone the Repository

    Clone the demoenvservicenowmcp source repository onto your local laptop (e.g. into your Documents folder):

    git clone https://github.com/vbiyani3107/demoenvservicenowmcp.git

  • Install Dependencies

    Open your command line / terminal, navigate to the folder, and run the NPM install command:

    npm install

  • Configure Credentials

    NEW STEP: Due to how Claude/Cursor routes MCP traffic, the local .env file is ignored. You MUST pass your credentials directly into the Claude/Cursor configuration file in the next step.

  • Configure Instances JSON

    Open config/servicenow-instances.json and update the dev instance block with your target URL and credentials.

    { "instances": [ { "name": "dev", "url": "https://your-instance.service-now.com", "username": "your_username", "password": "your_password", "default": true, "description": "Development instance" } ] }

3. Claude/Cursor Configuration

  • Locate the Configuration File

    For Claude: On Windows, open File Explorer and go to exactly this path:

    %APPDATA%\Claude\claude_desktop_config.json

    (If on Mac, the path is ~/Library/Application Support/Claude/claude_desktop_config.json)

    For Cursor: The global MCP configuration file is located at:

    ~/.cursor/mcp.json

    (Or configure it per-project at .cursor/mcp.json, or via Cursor Settings > Features > MCP Servers)

  • Add the MCP Server Routing

    Open that JSON file in a text editor like Notepad. Add the following object to map Claude/Cursor to our custom Node.js server.

    { "mcpServers": { "servicenow-demo": { "command": "node", "args": [ "<PATH_TO_HAPPY_PLATFORM_MCP>\\src\\stdio-server.js" ], "env": { "SERVICENOW_INSTANCE_URL": "https://<YOUR_INSTANCE>.service-now.com", "SERVICENOW_USERNAME": "<YOUR_USERNAME>", "SERVICENOW_PASSWORD": "<YOUR_PASSWORD>" } } } }

    A Quick Note on Client Logos

    Client logos are now passed dynamically at runtime! When you prompt Claude/Cursor to deploy a demo, simply drag and drop the target client's logo directly into the Claude/Cursor chat window and ask Claude/Cursor to use it. Claude/Cursor will process the image into Base64 format and seamlessly inject it into the ServiceNow platform using the Orchestrator API.

  • Restart Claude/Cursor

    Close and reopen the Claude/Cursor Desktop Application. You should now see a small "plug" icon next to your text box, confirming you are connected to the ServiceNow Demo tools.

  • Verify the Connection (Smoke Test)

    Before moving on, verify that Claude/Cursor successfully connected by opening a new chat and simply typing:

    "List all available ServiceNow tools."

    If Claude/Cursor natively replies by listing the SN-Deploy-Demo tool, your bridge is active and working perfectly!

4. How It Works (Hybrid Architecture)

The orchestrator is split across two runtimes so each side does what it's good at. You don't need to memorize this — but understanding it explains why deployment has two artifacts.

  MCP server (Node, your laptop)

Owns orchestration, validation, idempotency. Talks to ServiceNow over REST.

  • Users + role assignments
  • Incidents (idempotent on correlation_id)
  • Catalog categories, items, variables, choices
  • Widget-instance title overrides
  • Update-set wiring
  • Also covers: dashboard widget injection, reports, HR cases, purchase orders, hero container background.

  Script Include + Scripted REST (slim)

Owns only what genuinely needs Glide. Called by the MCP over HTTP.

  • POST /api/global/demo_orchestrator/branding — sp_theme CSS regex injection + base64 logo as sys_attachment
  • POST /api/global/demo_orchestrator/revert — bulk deleteMultiple() teardown across all demo tables (catalog, users, incidents, HR cases, POs, reports, sp_instance bindings) plus hero container reset

Why split? Bulk delete and CSS regex are dramatically faster as one server-side transaction than as N REST calls. Everything else is just as cheap (and far easier to debug) over REST.

Dashboard injection — first-column traversal: Instead of hardcoding sys_id references, the MCP traverses the portal layout dynamically:

  1. Queries sp_page where id is index (or whatever pageId the caller specifies).
  2. Queries sp_column with sp_row.sp_container.sp_page=<page>^ORDERBYorder, limit 1, to find the primary content column (top order).
  3. Creates an sp_instance record mapping the target widget (e.g. demo_kpi_dashboard) to that column. The sp_widget records themselves must already exist on the instance — Update Set / scoped app — the MCP only manages bindings.

5. ServiceNow Backend (Script Include + Scripted REST API)

  • One-shot deploy from your laptop (recommended)

    The repo ships with scripts/deploy_script_include.cjs, which idempotently creates/updates the Script Include AND its companion Scripted REST API definition + 2 operations in a single run. The Script Include source it deploys lives at servicenow/DemoOrchestratorAPI.js. Credentials come from environment variables only — copy .env.example to .env and fill it in, or pass them inline:

    SN_INSTANCE=your-instance.service-now.com \ SN_USERNAME=admin \ SN_PASSWORD='********' \ node scripts/deploy_script_include.cjs

    When it finishes you'll see the two endpoint URLs printed. That's all the ServiceNow-side setup the MCP needs.

6. Running the Engine

Your environment is now completely configured! You don't need any coding skills to run this. To create a massive, customized demo environment in seconds, you just ask Claude/Cursor to do it.

Available demo tools

SN-Deploy-Demo — one-call umbrella. Composes everything below in a single payload. Use this 95% of the time.

For surgical edits Claude can also call any of these directly:

  • SN-Demo-Apply-Branding — visual branding (CSS + base64 logo + optional hero container background)
  • SN-Demo-Apply-Personas — users + roles
  • SN-Demo-Apply-Data — incidents, plus optional HR cases (sn_hr_core_case) and purchase orders (proc_po), plugin-gated
  • SN-Demo-Apply-Catalog — categories + catalog items + variables + choices
  • SN-Demo-Apply-Widget-Overrides — relabel sp_instance widget titles
  • SN-Demo-Apply-Reports — sys_report rows used by demo dashboards (idempotent on title)
  • SN-Demo-Apply-Dashboard — bind existing sp_widget records to the index page's first column as sp_instance rows; clientPrefix-stamped for clean revert
  • SN-Demo-Revert — bulk teardown by clientPrefix (server-side deleteMultiple())

Option C: Reverting a Demo

Wiping a client demo is a one-liner too. The Script Include's revertByPrefix() uses deleteMultiple() server-side, so even a 200-record demo collapses in under a second — including stripping the master CSS override from every Service Portal theme.

Revert the [CLIENT PREFIX] demo by calling SN-Demo-Revert with that clientPrefix.
